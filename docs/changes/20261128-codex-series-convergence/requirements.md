## 1. 背景、用户故事与成功定义

个人及 1–5 人团队需要在 VS Code、CLI、Remote SSH、Linux/Windows、GitHub/GitLab Self-Managed 环境中完成需求、缺陷、提交前检查、交付、诊断与故障修复。嵌入式 C/C++、MCU、RTOS、Linux/BSP、音频/控制算法及 OTA 需要深层语义和真实测试证据。重复通用 Agent、重复工作台、重复治理和低价值模型调用挤占真实研发投入。

- U1：开发者只需原生 Codex/VS Code 与现有 Git/CI 即可研发；简单提交和常规控制无模型费用。
- U2：审查者能知道哪些内容被读取、哪些实际验证、哪些未知；跨文件缺陷有可核实锚点，不以一致性冒充召回。
- U3：维护者可独立管理多个 GitLab 实例、明确失败和重试状态、追溯预算、恢复故障，不泄露其他实例数据。
- U4：嵌入式研发者从真实故障证据进入因果分析及受控修复，未证明的根因或修复不能标记已确认。
- U5：多人多仓多主机下能准确找到阻塞会话并回到原生 Codex；需求和缺陷仍由业务平台管理。
- U6：维护者只需维护有用户价值的资产、契约和分发链；正式发布与真实现场结果可核实。

## 2. 约束与非目标

不新增仓库、通用 Agent 平台、第二个任务权威、中央调度数据库或新的模型竞争控制面。不引入 Spec Kit/OpenSpec 运行时、双向桥或通用兼容框架。无活跃消费者的旧代码删除，但不得用删除测试、绕过门禁、静默降级来达到精简；历史 Git、证据及有保留义务的数据继续保全。真实迁移仅以明确旧部署存在及恢复需求为条件；不提供虚构兼容。只允许公开、许可已核实或用户明确批准且符合数据边界的实验语料；不得发布私有代码、日志、会话、主机信息、凭据。实验须先有独立明确授权的计费身份与预算，不消耗未批准额度，不以估算冒充账单。禁止自动扩权及未经授权的 Git 远端写入、生产重启、设备写入/OTA、删除与发布。

## 4. 优先级与冲突处理

P0：R01、R02、R07、R08、R16 的安全/生产边界；R04 关键覆盖缺口。P1：R03、R05、R06、R09–R14 的价值和风险改进；R15 真实依赖退役。不可为了 Token、延迟、代码量或发布进度降低安全、数据隔离、高危召回或覆盖诚实性。指标由 [verification.md](verification.md) 冻结；未测基线不得假称提升。若确实无法同时满足收益目标与安全目标，保留 baseline 并公开差距；只有证据证明无收益的候选才退出，不反复优化到伪通过。

## 5. 变更控制

小改用已有项目流程；本计划拆为各仓内有界 SDD 子变更，使用 Rxx/Txx/Vxx 关联，避免每仓复制本文。重大范围变化先在此计划 PR 中更新需求；各仓现有机器合同优先描述当前实际行为，计划不是运行时权限。验收按 [tasks.md](tasks.md) 与 [verification.md](verification.md)，待真实交付后再归档完成结论。
